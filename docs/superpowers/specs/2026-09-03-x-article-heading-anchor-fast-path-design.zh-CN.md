# X Article：标题锚点与可控耗时 Fast Path

- 日期：2026-09-03
- 状态：对话设计已确认；书面规格待审阅；尚未实施
- 执行方式：当前任务 inline，不派 Subagent
- 依赖：现有 X Article Fast Path、Complete Host Bridge 与软预算 V2

## 1. 要解决的问题

2026-09-02 的草稿物化暴露了两类失败：第一张正文图从封面完成到成功上报约 2 小时 22 分钟；7 张图片全部位于章节末尾，却通过了数量与位置序号校验。

已确认的原因是：英文母稿先把图片排在章节末尾，计划与浏览器照此执行；正式物化又混入了 Host 调试、代码修改、测试和构建。完整观察存在重复；其具体耗时占比尚未测量。局部轮询在 `await observe()` 返回后才检查超时，不能单凭这个检查保证观察调用本身及时返回。

本次选择在现有执行器上小范围改动：标题语义锚点负责正确位置，连续执行与精简观察负责缩短正常路径，无进展暂停负责限制异常空转。

仅改锚点不足以解决速度；正文与图片整体导入缺少可靠验证，不纳入本次实现。

## 2. 目标与边界

| 项目 | 约定 |
|---|---|
| 正常时长目标 | 1 张封面 + 7 张正文图，完整草稿物化不超过 15 分钟 |
| 正文单图目标 | 不超过 90 秒；60～90 秒是预期参考，不是已实现性能 |
| 总耗时超标 | 软提醒，保留有效授权，不因到达 15 分钟而强制结束 |
| 无进展 | 连续 180 秒没有新的可验证里程碑，暂停队列并保存现场 |
| 完成边界 | 草稿已保存、内容及图片位置通过验证；不包含 Preview 或 Publish |

15 分钟针对上述代表性工作量，不限制文章只能有 7 张图，也不把相同目标强加给任意图片数量。性能目标与正确性分别报告；功能通过但超时，不能称为性能优化已经达标。

复用一次 Digest 绑定确认、账号/Draft/内容/素材边界、逐图 claim/report、checkpoint、已有重试与只读恢复额度。保留现有 Preview/Publish 权限隔离。

## 3. 标题锚点：从母稿到浏览器同一规则

以后有配图的章节默认排列为：**章节标题 → 对应图片 → 章节正文**。无配图章节保持原样，不强制每章生成图片。

每张正文图在 Article Package 中声明语义位置，最小结构为：

```yaml
placement:
  kind: after_heading
  heading_id: project-knowledge-changes-state
  heading_text: Project Knowledge Changes State
```

- `heading_id` 在当前文章包内唯一；`heading_text` 是该包中标题的确切文本，用于审计和核对。
- 标题重复时必须使用明确的唯一 ID 绑定；只有文本而无法唯一定位时，在本地预检失败，禁止浏览器模糊匹配。
- 图序由文章包明确声明。同一标题绑定多图时，按声明顺序组成紧跟标题的图片组；正文在整组图片之后。
- 母稿和发布稿的 Markdown 本身必须体现这一排列；不允许只修改发布计划而保留一份顺序不同的最终母稿。中英文分别校验各自的标题绑定。
- 编译器把语义位置转换为现有 visual anchor/ordinal；占位锚点生成在对应标题后。Host 校验标题与相邻锚点的关系后执行；ordinal 仍用于结构一致性校验，不再是唯一的正确性标准。
- 生成配图及其说明时一并提供章节绑定、图序、Alt；此次不要求重新生成已有图片字节。

本地 Audit 展示简洁的“标题—图片—标题后”映射，纳入已有的一次确认，不增加逐图确认。最终验收必须确认标题后是正确图片或图片组，而不只是确认图片总数。

职责保持清晰：仓库内文章/配图指导负责声明并生成正确位置；Harness 负责校验、编译和授权；Host 负责页面执行与证据；状态记录负责计时。全局 Skill 的实际部署是后续独立步骤。

新规则不静默迁移已批准的文章包、计划或正在执行的旧 Draft。移动旧草稿图片会改变内容顺序，需修正本地包、生成新的准确 Audit，再获得一次对应确认。

## 4. 正常路径：连续执行，逐图提交结果

仍使用现有 Chrome 登录态和 Complete Host Bridge。同一会话中串行消费已授权命令，不并发操作同一编辑器，也不将多张图片合并到一个 claim。

每张图的正常路径固定为：

```text
校验并定位标题后的锚点
→ 上传已绑定的素材
→ 必要时完成 Edit media / Apply
→ 确认当前图片已出现
→ 填写 Alt
→ 完整写后观察、保存验证与 report
→ 下一张
```

执行器封装已知步骤，减少模型在正常路径中的逐步重复调度；遇到未知页面形态时报告异常，不在任务中手写另一套上传逻辑。复用会话和静态已验证输入，但不复用失效的 DOM 元素引用。

观察分工：

1. 运行开始：完整预检账号、文章包、内容、素材和计划布局；已有 Draft 直接对账，新 Draft 在获准创建并导入后建立页面锚点基线。
2. 单图上传期间：只观察当前锚点、图片和媒体对话框；根据明确状态等待，不循环生成整篇完整报告。
3. 单图 Alt 完成后：局部等待保存完成，再做一次完整写后观察，核对素材身份、位置、Alt、内容完整性和保存状态；成功后立即写 checkpoint。
4. 全部完成：全篇布局及内容对账。最后一张的观察若仍新鲜且包含全部必要证据，可复用；发生页面变化则重新观察。

上述优化不省略素材身份或内容完整性校验，也不把缩小观察范围解释为允许未验证的写入。

## 5. 180 秒无进展暂停

这是活动执行的进展约束，不是重新引入 15 分钟硬截止。约束覆盖封面、正文图和命令之间的调度空档；首个命令从执行开始计时，之后从最近一次可验证进展计时。

可验证里程碑是当前命令首次达到的有限状态，例如：唯一标题/锚点已验证、文件已交付、媒体已出现、Apply 已完成、Alt 已保存、完整写后报告成功。事件必须带命令和素材身份，并有对应的工具或页面证据。

重复截图、相同轮询结果、相同状态来回变化、重新下发同一动作、模型推理、改代码和测试均不算新进展。里程碑按同一执行、素材和语义阶段去重；新 attempt/claim ID 不使相同里程碑重新计为进展。重试、Host 重连或恢复不能清空已完成里程碑、重试计数和累计时长。

执行器负责进展检查，而不是等主任务下次想起查看。底层观察及浏览器等待也必须有有界等待或取消机制；不得只在 `await` 返回后才发现已经超时。

达到无进展条件时：

1. 先持久化暂停状态、最后成功 checkpoint、当前命令、已知页面状态、失败阶段和时间。
2. 阻止新 claim 与后续浏览器写步骤；能够取消的在途等待请求取消。
3. 取消不等于回滚已发出的请求。无法确认结果的在途动作标为“结果未知”；晚到结果保留为对账证据，不自动继续队列。
4. 未确认在途动作结束且完成只读对账前，不再上传同一素材。单独的超时返回或 `Promise.race` 不足以证明后台写操作已经停止。
5. 向用户报告卡在哪一步和最后进展；不自动新建执行、恢复、重派代理或扩大重试额度。

恢复需用户明确继续，先在现有许可额度内只读对账，再决定剩余动作；额度耗尽时保持阻塞。用户明确暂停期间不运行活动无进展计时；恢复开启新的活动计时间隔，但原始开始时间、已耗时、失败历史和重试额度不重置。

## 6. 运行与修复分开

一次物化使用记录在案的固定 Harness 构建。复用现有版本信息，不新增一套 Host 版本握手或素材绑定系统。

运行过程中不改 Harness、不重新构建、不部署 Skill、不运行开发测试。未知缺陷出现后保存 checkpoint 并结束本次活动执行；修复、回归与构建在明确的开发阶段进行。修复后经明确继续，从对账开始恢复，不能借修复自动获得新上传或发布权限。

流程可以在同一 Codex 任务中进行，但必须切开开发与发布两个活动阶段；默认 inline，不创建额外监控任务或 Subagent。

## 7. 计时与报告

计时起点是确认后首次开始 Fast Path 执行；包含预检、导入（若需要）、定位、上传、调度、重试和最终对账。不包含执行开始之前的文章写作、图片生成和开发。

使用现有进度记录增加分段耗时：预检/导入、定位、文件交付与上传、Edit media/Apply、Alt、观察与保存验证、调度空档。报告当前图序、阶段、累计耗时及上次可验证进展；不输出无意义的重复轮询记录。

- 每次事件在真正发生时记录，不能提前绑定整次运行共用的 `observed_at`。
- `completed_at` 只在最后一项必要验证通过并持久化终态时写入，不得早于最后成功事件；总耗时由同一计时口径计算。
- 原始墙钟开始时间跨恢复保留；显式暂停、等待用户和独立修复的区间单独列出。既报告用户经历的总墙钟时长，也报告活动物化耗时，不能通过分段隐藏总等待。
- 3 分钟约束是故障控制；15 分钟是软提醒。两者在报告中明确区分。

## 8. 验收

1. 母稿、编译后计划、编辑器观察均满足标题—图—正文顺序；复现“图在章节末尾但 7/7”时必须失败。
2. 标题缺失、歧义或图绑定错误在本地失败；标题下多图按声明顺序验证，其他章节正文不能被移动。
3. 正常路径每张图只交付一次文件；重复 report、断线后的已完成图片和延迟结果不造成重复上传。
4. 单图中间观察不反复做整篇提取；末次完整观察仍验证账号、Draft、内容、图片位置、Alt 和保存状态。
5. 用可控时钟测试 180 秒无进展、观察不返回、重复伪进展、命令间空转和超时后晚到结果；暂停后不再派发新的写步骤，已发在途动作的晚到结果进入对账，不触发续跑。
6. 超过 900 秒但仍有真实进展时只提醒；既有权限、重试上限、只读恢复额度和 Preview/Publish 禁止测试保持通过。
7. `completed_at`、最终成功事件和 elapsed 不再相互矛盾；跨暂停/恢复能解释总墙钟和活动耗时。
8. 保留 0/1/7/10 张正文图的自动化覆盖；封面单独处理，不把数量写死为 7。
9. 经授权先做单张真实验证，再做 1 张封面 + 7 张正文图的完整计时。真实验证包括最后版式核对，不以模拟测试或图片数量代替。
10. 完成报告分别给出正确性、性能实测、异常暂停和剩余限制。首次达标只能证明该次样本，不宣称已稳定达到长期性能目标。

## 9. 本次不做

- 不增加并发编辑、自动重装浏览器扩展、自动切换浏览器或登录方式。
- 不研究正文与图片整体导入，不实现通用 Markdown 编辑器。
- 不修改当前 X 草稿、不移动其图片、不创建新 Draft、不 Preview、不 Publish。
- 不直接更新全局 Skill 或研究记忆；相关部署、记忆写入和真实 Draft 修正仍按各自授权边界进行。

## 10. 书面规格自检

规格只覆盖标题位置、正常路径耗时、无进展暂停与计时证据。15 分钟与 180 秒语义互不冲突；批量会话保持逐图事务；旧计划不静默迁移；取消与已发生副作用严格区分；性能目标明确标为待实测。实施计划在用户审阅此文件后编写。
